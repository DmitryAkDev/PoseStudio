# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

PoseStudio is an early-stage, open-source Qt6/C++ desktop application for 3D character creation, posing, and scene building. The codebase today is a main window shell, an asset manager side panel backed by SQLite, a Preferences dialog, a menu bar, and a Vulkan-backed 3D viewport (`src/viewport/`) that draws an infinite floor grid through a real orbit camera and renders lit, textured geometry — both Wavefront `.OBJ` models and **fully rigged, morphable character figures** imported from their native scene format (`.duf`/`.dsf`). The figure pipeline is now the largest part of the project: per-material-zone geometry + physically-based materials, baked character-shape morphs, a skeleton with GPU dual-quaternion skinning, joint-driven pose correctives, Catmull-Clark subdivision, and an interactive posing UI (click-a-joint + rotate gizmo, anatomical joint limits, full-body IK via Ctrl+drag — ground-anchored FABRIK with auto-balance, see `scene/ik/` — pose save/load, undo/redo) — see the 3D Viewport section below. The viewport also offers a selectable shade-mode picker (twelve modes including a photoreal PBR mode), MSAA anti-aliasing, and image-based lighting (IBL) from an HDR environment — with an Environment properties tab for live control (the analytic key/fill/rim rig is retained for the non-photoreal shade modes). The animation/timeline systems and final-frame (production) rendering described in README.md are still roadmap — they don't exist in code yet.

## Build

Requires Qt 6 (developed against 6.11.1, MSVC 2022 64-bit), CMake 3.21+, and the **LunarG Vulkan SDK** (https://vulkan.lunarg.com — supplies the Vulkan headers, loader, validation layers, and the `glslc` shader compiler). `find_package(Vulkan REQUIRED)` aborts configuration with a clear message if the SDK is absent, so the viewport can't be built without it.

```
cmake -B build -DCMAKE_PREFIX_PATH="C:/Qt/6.11.1/msvc2022_64"
cmake --build build
```

If `CMAKE_PREFIX_PATH` isn't passed, `CMakeLists.txt` falls back to the hardcoded path `C:/Qt/6.11.1/msvc2022_64` — never commit a change to that fallback to point at your personal Qt install.

GLM (math), AMD's Vulkan Memory Allocator (VMA), tinyobjloader (the OBJ importer's parser), stb_image (`.hdr` environment loading), and tinyexr (`.exr` environment loading) are pulled in header-only via CMake `FetchContent` at pinned tags/commits (see the "3D VIEWPORT DEPENDENCIES" block) — a fresh clone needs only Qt + the Vulkan SDK, nothing vendored. tinyobjloader, like VMA, stb_image, and tinyexr, is a single-header lib whose implementation is compiled in exactly one TU (`import/obj/objimporter.cpp` via `#define TINYOBJLOADER_IMPLEMENTATION`; stb_image in `viewport/stb_impl.cpp` via `#define STB_IMAGE_IMPLEMENTATION`; tinyexr in `viewport/tinyexr_impl.cpp` via `#define TINYEXR_IMPLEMENTATION` — its ZIP inflate rides on the miniz sources already compiled into the target, so no zlib). They're *populated* (downloaded) but their own CMake isn't run; we consume their headers directly via `target_include_directories`. GLM's Vulkan-convention flags (`GLM_FORCE_RADIANS`, `GLM_FORCE_DEPTH_ZERO_TO_ONE`) are set once project-wide as `target_compile_definitions` — never per-file, or translation units disagree on matrix layout (a silent-corruption bug).

The **native figure importer** (`import/figure/`, see the 3D Viewport section) adds two more `FetchContent` deps under the same no-configure treatment: **nlohmann/json** (header-only JSON, kept out of Qt so the importer core stays Qt-free — `QJsonDocument` would drag Qt in) and **miniz** (to inflate gzip-compressed scene files). miniz isn't header-only — it ships C sources — so two accommodations exist: (1) `project()` enables the **C** language (`LANGUAGES C CXX`) — without it CMake silently classifies miniz's `.c` files as non-buildable `<None>` and they never link; miniz's split sources (`miniz.c`/`miniz_tinfl.c`/`miniz_tdef.c`/`miniz_zip.c`) are compiled directly into the target via `target_sources`; and (2) a tiny shim header `cmake/miniz-shim/miniz_export.h` (on the include path) satisfies miniz.h's `#include "miniz_export.h"` — that file is normally generated by miniz's CMake, which we skip; for a static in-binary build its export macros are no-ops.

The build links `Qt6::Widgets`, `Qt6::Gui`, `Qt6::Sql`, `Qt6::Concurrent` (the off-thread IBL bake), and `Vulkan::Vulkan` (the loader; `QVulkanInstance`/`QWindow` live in Qt6::Gui). No Qt Network/3D/Quick modules. `CMAKE_AUTOMOC`/`AUTOUIC`/`AUTORCC` are all on, so new `Q_OBJECT` classes, `.ui` files, and resources just need to be added to the `add_executable` source list / `resources.qrc` — no manual moc/rcc invocation.

Two post-build mirror steps copy on-disk content next to the executable on every build (both true mirrors — `rm -rf` then `copy_directory`, not overlays, so renamed/removed source files don't linger): (1) `resources/Maquettes/` (the built-in asset library, real on-disk content — not embedded via `resources.qrc`, since the Asset Manager browses libraries through `QDir`, not Qt's resource filesystem); and (2) the compiled SPIR-V shaders. Shaders are GLSL under `src/viewport/shaders/`, compiled to `*.spv` by `glslc` via a per-shader `add_custom_command` (gated through the `PoseStudioShaders` custom target that `PoseStudio` depends on), then mirrored to `<applicationDirPath>/shaders` where `VulkanRenderer` loads them at runtime. Add a new shader by dropping the `.vert`/`.frag` in that folder and appending its name to the `SHADER_SOURCES` list in `CMakeLists.txt`.

**Cross-platform posture**: PoseStudio is meant to be fully cross-platform (Windows, macOS, Linux). The stack is portable by construction — Qt6, C++17, CMake, SQLite, Vulkan — and the codebase carries no `#ifdef` platform branches; platform differences are absorbed by Qt (window/surface creation via `QVulkanInstance`/`QWindow`) and CMake rather than hand-written per-OS code. Accommodations already in place: writable data lives in `QStandardPaths::AppDataLocation` (an installed app's own directory is read-only on macOS/Linux — see the Database section); the Windows icon resource (`resources/PoseStudio.rc`) is added to the target only `if(WIN32)`; and because macOS runs Vulkan through **MoltenVK** (a Vulkan-on-Metal translation layer), `VulkanContext` enables the spec-mandated `VK_KHR_portability_subset` device extension whenever a device advertises it (a no-op on Windows/Linux). **Caveat:** only the Windows/MSVC build has been exercised so far — the macOS/Linux paths are correct by construction but unbuilt/unrun, and the one known runtime unknown on macOS is whether Qt's `QVulkanInstance` auto-adds the *instance*-level portability-enumeration extension (verify on real Apple hardware before claiming macOS support).

There is no test suite, linter, or CI configuration in this repo yet.

## Architecture

**Source layout**: `src/` is organized into one folder per subsystem — `core/` (non-visual services: database, preferences manager), `shell/` (app chrome: menu bar, splash/About overlay, Fusion theming), `assets/` (Asset Manager), `preferences/` (the Preferences dialog + every panel), and `viewport/` (the 3D engine, itself split into `rendering/` + `scene/` + `import/`). Only `main.cpp` and the cross-cutting `constants.h` sit at the `src/` root. Every subsystem folder is on the compiler include path (`target_include_directories` in `CMakeLists.txt`), so headers are included by bare name (`#include "database.h"`) regardless of which folder includes them — when you add a new `src/` subfolder, add it there too or its headers won't resolve.

**Startup sequence matters** (`src/main.cpp`): the SQLite database is opened and `PreferencesManager` is loaded *before* any widget is constructed, because widgets (e.g. `AssetManagerWidget`) read preferences/DB state during construction. If you add a new manager/cache that UI depends on, initialize it in this same early block, not lazily inside a widget.

**Database** (`src/core/database.{h,cpp}`): single named QSqlDatabase connection (`"db_conn"`) shared process-wide via `QSqlDatabase::database("db_conn")` rather than opened per-call. The SQLite file (`posestudio.db`) lives in the platform's per-user app-data dir (`QStandardPaths::AppDataLocation`, derived from the app name set in `main.cpp` *before* `initializeDatabase()` runs) — not next to the executable, whose directory is read-only for an installed app on macOS/Linux. Older builds stored it next to the `.exe`; `initializeDatabase()` performs a one-time *move*-migration of that legacy file into the new location on a Normal launch (copy-then-delete, so a later Factory Reset can't resurrect it), and FactoryReset also clears any lingering legacy file. Schema lives in `resources/database/initialize.sql`, embedded into the binary via `resources.qrc`, and is executed both on `DbInitMode::FactoryReset` (which also deletes the existing file first, and is reachable from the app via Preferences → Factory Reset) *and* on a genuine first launch (no `posestudio.db` file yet) — `initializeDatabase()` checks `QFile::exists(dbPath)` *before* FactoryReset can delete it, so a fresh install always gets the schema even via `DbInitMode::Normal`. There is still no formal migration system, but additive schema changes for existing databases (new columns/tables) are applied unconditionally at the end of `initializeDatabase()`, each guarded to be a no-op once already present (e.g. a `PRAGMA table_info` check before `ALTER TABLE ADD COLUMN`, or `CREATE TABLE/INDEX IF NOT EXISTS`) — add new ones here rather than only in `initialize.sql`, or pre-existing installs will silently fail at the first query touching the new column/table. **Gotcha:** `initialize.sql` is executed by a naive `;`-splitter — no statement, including comments, may contain a semicolon. A 0.3.6 header comment (`split on ';'`) broke a statement boundary and corrupted `CREATE TABLE Preferences` on every fresh install (the table silently missing, `PreferencesManager` failing at bootstrap with "no such table: Preferences"); a `CREATE TABLE IF NOT EXISTS` repair migration in `initializeDatabase()` fixes affected databases in place.

`AssetLibraries` has an `AssetLibraryIsBuiltIn` flag for the one library that ships with the app ("Maquettes", at `<applicationDirPath>/Maquettes`): `initializeDatabase()` re-syncs that row's path to the current install location on every launch (in case the app moved) and `mkpath`s the folder as a safety net. Built-in libraries always sort first (`ORDER BY AssetLibraryIsBuiltIn DESC`) and are excluded from the user-manageable list in Preferences → Assets, but still appear/behave like any other library in the Asset Manager tree. `initializeDatabase()` also creates a **default user library** — "My PoseStudio Library" in the user's Documents, registered as an ordinary (non-built-in, fully user-manageable) library — but only on the very first launch (a `UserLibraryCreated` flag row in Preferences) and only if no non-built-in library by that folder name is already registered, so an existing library is honoured and a deliberate later rename/removal isn't fought on every start. This library is the user-facing home for personal content the app itself consumes: its `hdri/` subfolder is where the Environment panel and the viewport's default environment find HDRI panoramas, resolved via `LibraryPaths::userLibraryRoot()/hdriDirectory()` (`src/core/librarypaths.{h,cpp}` — DB lookup by folder name, Documents fallback).

`Favorites` (`FavoriteID`, `FavoritePath` unique, `FavoriteSortOrder`) is a flat list of favorited asset file paths — no folders, no nesting. `FavoriteSortOrder` holds the user's manual drag order from the Favorites pane (see Asset Manager section below); new favorites append after the current max.

**Preferences manager** (`src/core/preferencesmanager.{h,cpp}`): a process-wide singleton (`PreferencesManager::instance()`) that loads the entire `Preferences` SQLite table into a `QHash` once at startup. Reads never touch the DB; writes update the cache and persist immediately. It is explicitly not thread-safe — only call it from the Qt GUI thread.

**Asset manager** (`src/assets/assetmanagerwidget.{h,cpp}`, the largest file in the project): the side-panel widget that browses physical asset library folders (paths stored in `AssetLibraries`) alongside virtual, user-defined "Collections" (`AssetCollections`/`AssetCollectionItems` tables) and a flat "Favorites" list (`Favorites` table). Collections can nest arbitrarily deep via `AssetCollections.AssetCollectionParentID` (`0` = top-level) — any collection, at any depth, can hold its own flat asset items alongside further sub-collections (folder *shortcuts* inside collections were removed in 0.1.3 — a collection holds assets and sub-collections only). Favorites, by contrast, is intentionally flat — no folders, no sub-favorites, just asset items. `contextForTreeItem()` walks a tree item's ancestor chain to classify it as `Library`/`Collection`/`SearchResults`/`Favorites` regardless of nesting depth; prefer it over checking a node's immediate parent when context-menu or grid logic needs to know which "world" an item belongs to. Tree root order is Search Results, Favorites, Collections, then physical libraries (built-in libraries first). Key pieces:
- `AssetFolderProxyModel` wraps the filesystem `QStandardItemModel`-backed tree to mark folders as direct/indirect "hits" (i.e. contain or descend into a folder containing matching assets) for search/filtering, with results debounced via a pending-index queue rather than recomputed synchronously.
- `AssetTreeDelegate` / `AssetGridDelegate` fully override Qt's default painting for the directory tree and the thumbnail grid respectively — don't expect standard `QStyledItemDelegate` behavior; geometry constants they rely on (icon size, margins, gaps) are centralized in `src/constants.h` so the two delegates' size hints can't drift apart.
- Breadcrumb rendering is cached per `displayFolder()` call (`m_breadcrumb*` members) and only re-laid-out, not recomputed, on label resize. Virtual sources (Collections, Favorites) instead show a plain title (`m_currentTitleText`); `displayFolder()` and `refreshTitleLabel()` both branch on the same "is this a virtual path" check (`COLLECTION_` prefix or `FAVORITES_ROOT`) — keep them in sync if a third virtual source is ever added.
- Physical folders and DB-backed virtual Collections/Favorites are all rendered into the same `QTreeView`/`dirModel`, distinguished by `searchResultsRootItem`/`favoritesRootItem`/`collectionsRootItem` root nodes — when adding tree behavior, check which subtree (filesystem vs. virtual) an index belongs to before assuming filesystem semantics (e.g. rename-on-disk) apply.
- `buildAssetHits()` resolves a flat list of asset paths into thumbnailed `AssetHit`s (shared by `parseCollectionAssets`/`parseFavorites`); it groups by folder internally for efficient thumbnail scanning but always re-emits in the caller's *input* order — both Favorites and Collections rely on this to preserve the user's manual drag order, so don't reintroduce a hash-ordered return here.
- Both Favorites and Collections are sortable grids backed by their own per-row order column (`Favorites.FavoriteSortOrder`, `AssetCollectionItems.AssetCollectionItemSortOrder`); `AssetManagerWidget::isSortableView()` (true when `m_currentFolderPath` is `FAVORITES_ROOT` or a `COLLECTION_*` id) is the single gate for both the drag-reorder handling and the "Sortable" info-bar label — check it rather than re-deriving the same `FAVORITES_ROOT`/`COLLECTION_` checks elsewhere. The drag-to-reorder itself (`beginGridDrag`/`endGridDrag`/`gridInsertIndex`/`updateGridDropIndicator`/`persistGridOrder` + the `MouseButtonPress/Move/Release` block in the grid viewport's `eventFilter`) is a **hand-rolled** drag, not Qt's `QListWidget` `InternalMove`: in `IconMode`, Qt's built-in internal-move free-positions the icon instead of reordering rows, and its `QDrag` runs through the OS drag loop. The manual version tracks raw mouse events, floats a translucent ghost `QLabel` plus a between-items drop-line indicator, leaves the grid untouched until release (moving items mid-drag would reflow the layout under the cursor), and auto-scrolls via a `QTimer` when the cursor sits in the top/bottom edge zone. `persistGridOrder()` branches on which view is current to write back to the right table/column. `AssetGridDelegate::paint` checks a `gridDragging` dynamic property on the grid to suppress the hover highlight while this is active.

**Styling**: dark theme enforced via `app.setStyle(new AppProxyStyle("Fusion"))` in `main.cpp`, never the native OS style. `AppProxyStyle` (`src/shell/appproxystyle.h`) must be constructed with `"Fusion"` explicitly — a bare `AppProxyStyle()` wraps the platform *default* style (e.g. `QWindows11Style` on Windows) instead, silently defeating the whole point of forcing Fusion. All app-level theming (style + global tooltip animation toggles) lives in this one spot in `main.cpp`'s "Branding & theming" block, not scattered into widget constructors. **Menu drop shadows:** an app-wide event filter (`MenuShadowFilter`, installed on `qApp` in that same block) sets `Qt::NoDropShadowWindowHint` on every `QMenu` at its `Polish` event (before the native window is created). This is because the menus' `border-radius` (in `_menumanager.qss`) makes each menu a *translucent* popup window, which Windows would give a heavy native drop shadow — the filter strips that shadow app-wide while keeping the rounded corners (menu-bar dropdowns, submenus, context menus, and the viewport shader menu alike). **Gotcha:** `NoDropShadowWindowHint` also flips the popup to an *opaque* window on Windows — the filter re-asserts `Qt::WA_TranslucentBackground` to bring back the see-through corners, but that still leaves a 2-3px opaque black speck at each sharp outer corner (the triangle outside the border-radius won't clear to transparent). So the filter *also* clips each menu to a rounded-rect **mask** (radius matched to the QSS `border-radius`, applied on the menu's `Resize`) to cut those specks away. All three together — no-shadow flag + translucent background + rounded mask — give rounded corners, cleanly transparent corners, and no shadow. Don't re-add a shadow via QSS (`box-shadow` isn't supported anyway); this is the single control point. Stylesheets are modular (`global.qss`, `_assetmanager.qss`, `_menumanager.qss`, `_preferences.qss`) and concatenated in `loadStylesheets()` (`src/main.cpp`) in a fixed cascade order — later files override earlier ones, so module-specific overrides belong in the `_*.qss` files, not `global.qss`. Some custom widgets (e.g. `AssetTreeView`) expose `Q_PROPERTY` values (like `separatorColor`) specifically so QSS can drive C++ painting logic. `QDialog`/`QMessageBox` are dark-themed globally too — but note Qt's QSS engine doesn't apply selectors (e.g. `a { color: ... }`) to rich-text `<a>` links inside a `QLabel`; those need the color set inline in the HTML string itself (see the "Add Asset Folder" hint label in `assetmanagerwidget.cpp` for the pattern). Also note: avoid declaring *any* `border` (even `border: none;`) on a `QListView`/`QListWidget` `::item` rule unless you actually want one — doing so flips Qt to full CSS box-model rendering of that item, which can visibly inflate the selection/hover rect beyond the item's actual layout cell (this is why `#AssetManagerTree::item` and `#AssetLibraryList::item` deliberately have no `border` line). `outline: none;` is fine on a container (`#AssetManagerTree`, `#AssetLibraryList`) to kill the dotted focus ring, but don't assume it's a no-op everywhere in the cascade.

**Destructive operations** (e.g. Preferences → Factory Reset, in `src/preferences/factoryresetpreferencespanel.cpp`): rather than trying to reconcile every widget's in-memory state (the asset tree, `PreferencesManager`'s cache, etc.) after wiping the database, the app just relaunches itself via `QProcess::startDetached(QApplication::applicationFilePath(), ...)` followed by `QApplication::quit()`. Follow this pattern for any future action that invalidates broad in-memory state rather than writing ad-hoc refresh logic for every affected widget. The reset itself is gated inline on the page (type "RESET" into a text field to enable the button) rather than behind a separate confirmation popup.

**Preferences dialog** (`src/preferences/preferencesdialog.{h,cpp}`, `src/preferences/preferencespanel.{h,cpp}`, `src/preferences/*preferencespanel.{h,cpp}`): a modal `QDialog` with a vertical tab list (left) driving a `QStackedWidget` (right). Each tab is a `PreferencesPanel` subclass living in its own file (`AssetsPreferencesPanel`, `FactoryResetPreferencesPanel`, etc.) so areas can be built out independently — adding a tab means adding a new subclass file and one `addPanel()` call in `PreferencesDialog`'s constructor, not touching the others. `PreferencesPanel` provides shared chrome (heading + top-aligned content layout) plus `addDescription()`/`addPlaceholder()` helpers for standardized body-copy styling — use these instead of hand-rolling a `QLabel` with inline font-size, or the panel won't match the others. `MenuManager::openPreferencesDialog(initialTab)` is the one entry point that opens the dialog (Edit → Preferences, and the Asset Manager's "Manage Asset Folders" context actions both route through it) and wires the `AssetsPreferencesPanel`'s `librariesChanged`/`navigateToLibraryRequested` signals back to the live `AssetManagerWidget` — `MenuManager::setAssetManagerWidget()` must be called (from `main.cpp`, after the Asset Manager tab exists) before that wiring can attach, so don't move `setupMenus()` to run after it without checking this dependency.

**3D viewport** (`src/viewport/`): a Vulkan renderer, hosted in a custom `QWindow` (not Qt's `QVulkanWindow` — we deliberately own the device/swapchain/render passes for the flexibility advanced rendering will need). The subsystem is split into a thin Qt-facing layer and a **Qt-free rendering core**, and that boundary is load-bearing — keep it:
- `ViewportWidget` (`viewportwidget.{h,cpp}`) is the *only* class the rest of the app sees. It's a plain `QWidget` that owns the process's `QVulkanInstance`, embeds the `VulkanWindow` via `QWidget::createWindowContainer()`, and degrades to an inline `QLabel` (rather than crashing the app) if `QVulkanInstance::create()` fails. `main.cpp` just news one up where the old viewport placeholder was. It also owns the teardown *ordering*: its destructor explicitly `delete`s the `createWindowContainer` wrapper (hence the `VulkanWindow` and all its Vulkan objects) **while the `QVulkanInstance` member is still alive**. Without that, the base `QWidget` destructor would free the window *after* the `QVulkanInstance` member is gone, and the renderer would call `vkDestroyDevice` on a device whose instance was already destroyed — a crash on close. Don't drop that explicit delete. **Overlay gotcha:** because the viewport is a *native* child window (`createWindowContainer`), it composites on top of ordinary sibling/overlay `QWidget`s — so anything that must paint over the viewport (the boot/About `SplashOverlay`, any future HUD) must be a **top-level window** (constructed with the `Qt::Tool` window type, then positioned over the parent in global coords), not a child overlay. Window *hints* alone (`FramelessWindowHint`, etc.) don't promote a parented widget to a window — `isWindow()` stays false and it remains hidden behind the viewport. **`Qt::Tool`, not `Qt::Window`:** a plain window type is a full application window, which X11/Wayland list in the taskbar and stack wherever the WM pleases (the strip and splash showed up as a second window BEHIND the main one on Linux); a tool window stays out of the window list and is kept above its owner (on macOS it is an `NSPanel`, which floats above normal windows and hides while the app is inactive). `ViewportWidget::eventFilter` also re-raises the strip on the main window's `WindowActivate` — deliberately not `ActivationChange`, which Qt also sends on DEactivation and would lift the strip over a modal dialog or the splash just as they take focus.
- `VulkanWindow` (`vulkanwindow.{h,cpp}`, a `QWindow` with `surfaceType == VulkanSurface`) is the Qt↔Vulkan bridge and the *only other* file in the subtree allowed to include Qt. It lazily builds the `VulkanContext` + `VulkanRenderer` on first `exposeEvent` (the platform surface must exist first), pumps one frame per `QEvent::UpdateRequest`, and routes mouse/wheel input to the camera. **Rendering is event-driven, not continuous:** a frame is drawn only when something requested one — every state change (camera input, posing, imports, shade-mode/lighting changes, environment-bake completion, expose/resize) calls `requestUpdate()`, so if you add a new way to mutate visual state, you MUST call `requestUpdate()` after it or the viewport won't repaint. `renderFrame()` re-arms itself only when `VulkanRenderer::drawFrame()` returns true (the swapchain was just rebuilt / the frame was skipped mid-rebuild, so one follow-up frame is needed). The old continuous re-arm redrew at full swap rate while idle and — with the then-FIFO/vsynced present — throttled the entire GUI thread; don't reintroduce it (a future animation playback should request frames from its clock instead). The swapchain now prefers `VK_PRESENT_MODE_MAILBOX_KHR` (FIFO fallback): tear-free, but presenting never blocks on the vertical blank, so an interactive drag's frame shows at the next scan-out instead of waiting a refresh — up to 16ms less input-to-photon latency. The usual power objection to mailbox doesn't apply precisely BECAUSE rendering is event-driven (no frames while idle, at most one per drag tick). **Camera drags are gated on `m_activeDragButtons`** — buttons whose press was actually seen *in this window* — not on `QMouseEvent::buttons()`: a modal dialog (e.g. the Import file picker) closing over the native child window can otherwise leak a button-held move to us and snap the camera, so a move only orbits/pans if its button's drag began here. **Right-click** (on release) opens an object context menu (`showObjectContextMenu`): it builds a world-space picking ray via `Camera::screenPointToRay`, asks `VulkanRenderer::pickModel` for the nearest model whose box the ray hits (box-level picking — `Model::intersectRay` slab-tests a static model's local bind bounds, but a POSED figure's world-space box of its live joints plus a 16cm flesh margin: full-body IK walks and crouches move the whole figure through the hip's pose translation, so after a walk the mesh sat far outside its bind box and the context menu lost its Delete entry while the joints, picked by live position, still worked; the renderer/scene own the geometry, so the window only deals in rays + model indices), and on "Delete" calls `VulkanRenderer::deleteModel`, which `vkDeviceWaitIdle`s before freeing so an in-flight frame can't reference the model's buffers. The `QMenu` popup is a top-level window, so it composites above the native viewport (unlike a child overlay — see the SplashOverlay note). It releases its Vulkan objects both on `QEvent::PlatformSurface`/`SurfaceAboutToBeDestroyed` (so they're gone before Qt frees the surface they reference) and in its destructor as a fallback — `releaseVulkan()` is idempotent. **Header gotcha:** `QPlatformSurfaceEvent` is pulled from `<QtGui/qevent.h>`, *not* `<qpa/qplatformsurfaceevent.h>` — the binary Qt install ships no qpa headers, so the seemingly-canonical qpa include fails to compile here.
- Everything under `rendering/` and `scene/` is **pure Vulkan + std + GLM, no Qt includes** (it takes `std::string` paths and `std::vector<char>` SPIR-V blobs, not `QString`/`QByteArray`). This keeps the engine core reusable and testable. Don't reach for a `Q*` type here just because it's convenient — push that concern up into `VulkanWindow` (e.g. `importObj` takes a `QString` at the `VulkanWindow`/`ViewportWidget` layer but hands a `std::string` to the renderer).

Ownership/lifetime is layered by how often things change: `VulkanContext` (instance handle, physical+logical device, queues, VMA allocator) is created once and lives until the surface dies. `VulkanSwapchain` (swapchain images, the shared depth buffer, render pass, framebuffers) is the resolution-dependent layer — `recreate()` rebuilds it on resize/out-of-date but deliberately *keeps the render pass* (it depends only on formats + sample count, which don't change). **MSAA:** the viewport renders multisampled — `VulkanContext::sampleCount()` picks the best of {4×, 2×} the device supports for both colour and depth (else single-sample), chosen once at device creation; the swapchain builds a transient multisampled colour target + a multisampled depth target and a render pass whose subpass **resolves** the MSAA colour into the (single-sample) swapchain image (attachment order colour(0)/depth(1)/resolve(2); the resolve attachment + `pResolveAttachments` only exist when `samples>1`, so there's a clean single-sample fallback). Every `VulkanPipeline` reads `context.sampleCount()` for its `rasterizationSamples` (all pipelines share the one MSAA render pass, so they must match). The renderer's two clear values (colour, depth) are unchanged — the resolve attachment is `DONT_CARE`/not cleared. This is what anti-aliases the figure silhouette. `VulkanRenderer` owns the per-frame state (command buffers, sync) and the swapchain plus the renderables — the `Scene` (imported meshes) and the `Grid` — and drives `acquire → record → submit → present`. Resize is coalesced: `notifyResize()` just sets a pending extent + flag (no-oping when the extent is unchanged — expose events report the current size too, and an un-obscure mustn't force a rebuild), and the actual rebuild happens at the next `drawFrame()` (on `VK_ERROR_OUT_OF_DATE_KHR`/suboptimal/the flag) after a `vkDeviceWaitIdle`; `drawFrame()` returns whether a follow-up frame is needed (see the event-driven-rendering note above). Sync follows the standard pattern with one subtlety — `imageAvailable` semaphores and `inFlight` fences are per *frame-in-flight* (`kMaxFramesInFlight`, in `vulkancommon.h`), but `renderFinished` semaphores are per *swapchain image* (a submit-signalled semaphore mustn't be reused until that image's present completes), so they're resized whenever the swapchain image count changes.

`VK_CHECK` (`vulkancommon.h`) throws `VulkanError` on any non-success `VkResult`; `VulkanWindow::initializeVulkan()` is the catch boundary. VMA is header-only and must be compiled in exactly one TU — `vma_impl.cpp` is that file (`#define VMA_IMPLEMENTATION`), bound to the statically-linked loader (`VMA_STATIC_VULKAN_FUNCTIONS 1`), which is why `VulkanContext` can call `vmaCreateAllocator` without supplying a function-pointer table.

`VulkanPipeline` wraps one `VkPipeline` + layout. The *shared* fixed-function state (dynamic viewport/scissor — so pipelines survive resizes untouched — triangle-list topology) lives in the class; the knobs that differ between pipelines are passed in a small `PipelineConfig` (push-constant size/stages, alpha-blend on/off, depth test/write on/off, cull mode, primitive topology + line width — `LINE_LIST` drives the posing skeleton overlay — plus optional vertex-input bindings/attributes and descriptor-set layouts). Add a field there only when a real use case needs it — don't expose all of Vulkan's pipeline state speculatively. The mesh path has two pipeline *variants* (opaque + transparent) sharing one shader/layout. **Frame structure:** each frame first records the **key-light shadow pass** (`Scene::recordShadowPass` — a depth-only render pass on the `ShadowMap` (`rendering/shadowmap.{h,cpp}`, D32 2048², single-sample, static depth-biased; TWO samplers over the one image — comparison/PCF for lit-tests plus a NEAREST non-comparison twin whose raw depths feed the ground shadow's PCSS blocker search) via `shadow.vert` (same skinning as `mesh.vert`, joint set bound at index 0) into an ortho frustum fitted per frame around the models **and their floor projections along the light** (a posed figure's bounds = its bind AABB unioned with the posed bone positions + a flesh margin — the bind box alone let a leaning head/arm cross the fitted map's edge, transient dark bands while posing) (so ground shadows land inside the map; skipped, map left fully-lit, when there are no casters — the light matrix then parks on a degenerate projection every receiver reads as lit); the fitted `lightViewProj` rides in the camera UBO); then the **offscreen HDR scene pass** (`rendering/hdrtarget.{h,cpp}` — linear RGBA16F with the same MSAA colour/depth/resolve structure as the swapchain pass, so every scene pipeline builds against *its* render pass unchanged; `resize()` rebuilds images/framebuffer but keeps the pass, so pipelines never rebuild) draws the scene in **LINEAR HDR** — `mesh.frag`'s PBR mode and `background.frag` no longer tonemap inline — starting with the **HDRI backdrop** (`background.vert/frag` — PBR mode only: a fullscreen triangle sampling the prefiltered environment cube along the per-pixel eye ray, depth test/write off, following the same exposure/rotation dials as the shading so backdrop and subject always agree; runs even with no models). - **Floor grid** (`scene/grid.{h,cpp}` + `grid.vert/frag`): an *infinite* ground grid. It is NOT line geometry — it draws one full-screen quad and the fragment shader reconstructs the world point on the `y=0` plane per pixel (ray/plane intersect of the unprojected near/far points), then draws anti-aliased lines via `fwidth` derivatives and fades them out with distance. It writes correct `gl_FragDepth` (so scene geometry occludes it) but is alpha-blended with depth-*write off* (a transparent overlay mustn't occlude things behind the mostly-invisible plane), which is why it's drawn last (after the opaque mesh layer). Its push constants are `viewProj` (vertex inverts it to unproject; fragment uses it for depth) plus the key light's matrix as its first three ROWS — an ortho·rigid transform's bottom row is always (0,0,0,1), and dropping it frees exactly one vec4 for the **shadow dials** (intensity/softness/reach, from the Environment panel's Shadow group) within the 128-byte push minimum. The pipeline binds the scene's set 3 (at index 0), declaring bindings 2 + 3 (the shadow map's comparison and raw-depth samplers): where the key light is occluded the fragment composites a **PCSS soft shadow** (percentage-closer soft shadows with contact hardening) under the grid lines — a Poisson blocker search over the raw depths measures the caster's height above the floor (the search radius shrinks with the Softness dial, and the CENTER is always sampled — sparse ring taps can all miss a small caster like a foot, which showed as salt-noise speckles inside crisp shadows), the PCF kernel radius grows with that height × softness, and the shadow's intensity fades toward the Reach distance — so the shadow is dark and crisp at the figure's contact points and widens/dissolves as it trails away, like a real area-light shadow. A per-pixel kernel rotation (interleaved-gradient hash) turns the sparse taps' banding into unstructured noise, and the world-space scales come straight from the light rows' lengths (no extra uniforms). This is what visually grounds the figure on the otherwise-invisible plane; the fixed calibration the dials scale (contact opacity, spread-per-softness, search radius) is named constants at the top of `grid.frag`. All look tuning (line colour, cell size, major-line interval, fade distance, shadow tint/opacity) lives as named constants at the top of `grid.frag`; there are no colored axis lines yet.

**Mesh rendering & model import**: `Scene` (`scene/scene.{h,cpp}`) is the mesh analogue of `Grid` — it owns the mesh pipeline, the per-frame-in-flight camera UBOs + descriptor sets (set 0), the shared set-1 layout + a 1×1 white fallback texture, and the list of imported `Model`s, exposing `addModel()` and a `record(cmd, camera, frameIndex)` the renderer calls before the grid. A `Model` (`scene/mesh.{h,cpp}`) is one imported file: a set of `Mesh`es (one per material group) under a shared transform, and it owns the `VkDescriptorPool` its meshes' set-1 descriptors come from (sized to its mesh count). Each `Mesh` owns device-local vertex+index buffers, a base color, an optional `VulkanTexture`, and a set-1 descriptor pointing at that texture (or the scene's white fallback when untextured — so one pipeline/shader serves both: `albedo = baseColor * white = baseColor`). GPU buffers go through `VulkanBuffer` (`rendering/vulkanbuffer.{h,cpp}`); textures through `VulkanTexture` (`rendering/vulkanimage.{h,cpp}`, an `_SRGB` sampled image with a full mip chain). Load-time transfers live in `rendering/vulkancommands.{h,cpp}`, which offers two paths: `submitImmediate` (one self-contained transfer = one submit + fence wait) and **`ImmediateBatch`** (record many transfers into a single command buffer, then one submit + one fence wait). `Model`'s constructor builds **one `ImmediateBatch` for the whole model** — every mesh's vertex/index buffers and texture record into it (via the batch-taking overloads of `createDeviceLocalBuffer` / `VulkanTexture`), and it's submitted exactly once. That's the key import-perf decision: the old per-resource `submitImmediate` cost ~3 blocking GPU round-trips *per mesh*, which dominated import time on models with many material groups; batching collapses it to one round-trip per model. Trade-off: all staging buffers are retained (via `ImmediateBatch::retain`) until that single submit completes, so peak staging memory is the sum across the model's meshes rather than one-at-a-time. The 1×1 white fallback texture still uses the plain immediate path (a lone one-off upload).

**Image-based lighting** (`scene/environment.{h,cpp}`, `rendering/iblmaps.{h,cpp}`, `viewport/environmentsource.{h,cpp}`): the PBR/default shading is lit by an HDR *environment*, not a hand-tuned rig — this is what replaced 3-point lighting as the default. `environment.*` (Qt-free core) generates a neutral **procedural studio** environment and bakes three IBL products on the CPU (no offscreen GPU passes — the codebase has no compute/render-to-texture infra; the heavy loops are multi-threaded via `parallelFor` from `rendering/parallelfor.h`, a tiny std-only helper shared by every CPU bake — millions of samples that would otherwise stall startup/HDRI switches for seconds): **9 SH coefficients** for diffuse irradiance (Ramamoorthi form; fed via the set-0 UBO every frame and reconstructed per-normal in `mesh.frag`), a GGX-**prefiltered specular cubemap** (`prefilterSpecular`, mip = roughness), and the environment-**BRDF LUT** (`integrateBrdfLut`) — the standard split-sum decomposition, with SH standing in for an irradiance cubemap. The BRDF LUT is environment-independent (roughness/NdotV only), so it's integrated once and reused; only the SH + prefiltered cubemap re-bake when the environment changes. `IblMaps` uploads the cubemap (RGBA16F, cube view, CPU-generated mip chain) + LUT (RG16F) and owns the images/samplers behind descriptor **set 3**; `Scene` owns the set-3 layout/pool/set. The CPU bake and the GPU upload are split so the former can run off the render thread: `bakeEnvironment()` (core, Qt-free) does the heavy CPU work (normalize + SH + prefilter) into a `BakedEnvironment`, and `Scene::applyBakedEnvironment()` does the fast GPU upload + set-3 swap (after a `vkDeviceWaitIdle`, since it swaps maps the pipeline samples). The procedural default is baked synchronously in the `Scene` ctor so set 3 is valid before the first frame. Real panoramas replace the procedural default: `environmentsource.{h,cpp}` is the **codec boundary** — kept in the Qt-facing layer so the render core stays image-codec-free, exactly like model-texture decoding — whose `loadEnvironmentImage()` decodes an equirectangular panorama into an `EnvironmentImage`, dispatching on extension: Radiance `.hdr` via `stb_image`'s `stbi_loadf`, OpenEXR `.exr` via tinyexr's `LoadEXR` (declarations from `<tinyexr.h>`; implementation TU `tinyexr_impl.cpp`). `VulkanWindow` loads `<appDir>/environment.hdr` or `environment.exr` (explicit override, `.hdr` checked first) or a panorama from the **user library's `hdri/` tree** (`LibraryPaths::defaultHdri()` — see `src/core/librarypaths.h`): the stock `Studio Small 09` by basename (extension-agnostic — `.hdr` or `.exr`) wherever the user filed it, else the first of `LibraryPaths::hdriFiles()` — the **recursive**, category-ordered scan (subfolders = categories, root files first) shared by the Environment panel's menu and its initial button text, so the three can't drift; no panoramas at all just leaves the procedural default. HDRIs are deliberately **user content, not build output** — they live in "My PoseStudio Library/hdri" (user-writable, browsable in the Asset Manager) where users drop their own `.hdr`/`.exr` files; nothing is mirrored next to the executable and packaging/installers are responsible for placing the stock set there. **The bake runs off the UI thread:** `VulkanWindow::beginEnvironmentBake` decodes + `bakeEnvironment`s on a `QtConcurrent` worker (watched by a `QFutureWatcher`) and applies the result on the GUI thread, guarded by a per-request id so a slower earlier bake can't clobber a newer pick — so switching HDRIs (the ~hundreds-of-ms CPU prefilter) never freezes the app; the viewport keeps rendering the current environment until the new one lands. `stb_image` and `tinyexr` are fetched via `FetchContent` (pinned) and each compiled in one TU (`stb_impl.cpp` / `tinyexr_impl.cpp`), same as VMA/tinyobjloader; tinyexr inflates through the target's existing miniz sources (`TINYEXR_USE_MINIZ`), adding no zlib dependency. **Live controls:** the exposure/diffuse/specular/ambient-fill/key (intensity + azimuth/elevation)/subsurface/rim/rotation/tonemap dials — plus the **Shadow group** (enable, intensity, softness, reach: enable off skips the shadow pass entirely in `Scene::recordShadowPass` and parks the light matrix on the always-lit degenerate projection; intensity rides to `mesh.frag` via `params4.z` (blends the figure's self-shadow toward lit) and to the grid via its push-constant dials vec4; softness/reach shape the grid's PCSS penumbra + dissolve) — are `LightingSettings` (`scene/lightingsettings.h`, a plain-POD contract), fed through the UBO (`params`/`params2`/`params3`/`params4`; the key *direction* is computed CPU-side in `Scene::record` from the azimuth/elevation dials into the UBO's `lightDir`, so every analytic shade mode follows it) and driven by the **Environment properties tab** (`src/properties/environmentpanel.*`, a right-docker panel) with no re-bake — only switching the HDRI re-bakes. **The key light auto-aims at the environment's sun on USER HDRI switches:** `bakeEnvironment` derives the environment's dominant light direction from the luminance-weighted linear SH band (`BakedEnvironment::dominantDir` + `dominantStrength` = |L1|/L0 directionality), and when a *user-initiated* bake lands (`beginEnvironmentBake`'s `autoAimKey` — true from `setEnvironmentFile`, FALSE for the startup bake, so a fresh launch shows the authored `LightingSettings` defaults), `VulkanWindow` sets the key azimuth/elevation dials to it (elevation clamped to [15°, 60°] — below-horizon suns can't ground-shadow, near-zenith ones drop the shadow straight down where it reads as a smudge; skipped when directionality < 0.1, i.e. overcast) and emits `lightingRestored` so the panel rows follow — so picking an HDRI re-aims the PBR shadow to where that environment's light visibly comes from, while the dials stay live for manual re-aiming. **In the PBR mode the key also follows the Rotation dial**: `Scene::keyLightDir` applies the inverse of the shader's environment-sampling rotation (mesh.frag's `rotateY` replicated CPU-side), so rotating the environment swings the key highlight and the ground shadow with the visible backdrop; the analytic modes keep the dials as plain world-space directions. **The HDRI selector is a `QPushButton` + `QMenu`** (the shader-picker pattern — NOT a `QComboBox`, see the styling note there), but the menu's content is a **`QWidgetAction` hosting a `QListWidget`** (`#HdriList`) rather than plain actions — a bare `QMenu` can't cap itself at N rows or show a real scroll bar. The list, rebuilt on every `aboutToShow` so files added/refiled while the app runs appear immediately, shows each panorama (`.hdr`/`.exr`) in the user library's `hdri/` tree **grouped by subfolder** — users categorize panoramas by moving them into subfolders, and each subfolder becomes a bold **category heading** — spaced off the previous section, with a hairline rule under the text (a disabled, unclickable `QListWidgetItem` painted by the file-local `HdriHeadingDelegate`, since QSS can't address individual items; uncategorized root files list first with no heading; a nested folder's heading reads `A/B`) — each panorama with a large (178×89) image **thumbnail** — a same-basename image file in the panorama's own (sub)folder, any common format, first hit wins (the stock previews are `.jpg`; **beware `.webp`: Qt only decodes it with the optional "Qt Image Formats" add-on installed**, so don't ship webp-only previews) — six rows tall with a scroll bar for the rest, the current environment highlighted + scrolled into view, and a left-aligned "Open HDRI Folder…" footer button under it. All its styling (tight rows, menu-style hover, dark scroll bar, the spin boxes' +/− arrow glyphs) lives in `_environment.qss`. **Gotcha:** Qt's style engine ignores QSS `padding-left` on a left-aligned `QPushButton` label (the text lays out from the border box), so the button's left inset for the environment name comes from a transparent spacer icon set in code, not the stylesheet. The analytic lights still live in the UBO for the non-IBL modes: only **Rendered** (mode 0) uses the full key/fill/rim rig; the other analytic modes (Toon/Clay/Lighting-Only/Flat) use just the key + ambient, and PBR uses only the key.

**Import subsystem** (`viewport/import/`): model import is a self-contained, Qt-free subsystem (same "engine core = std + Vulkan + GLM, no Qt" rule as `rendering/`+`scene/`), structured so new formats slot in without touching the renderer, the dispatch, or existing importers. Its center is a **format-neutral IR** — `ModelData`/`MeshData` (`import/modeldata.h`) plus the shared `Vertex` layout (`import/vertex.h`, the geometry contract importers produce and `Scene` uploads) — that carries no format identity of its own. Each importer implements the `MeshImporter` interface (`import/meshimporter.h`: `displayName()` / `extensions()` / `load(path) → ModelData`, throwing on failure), lives in its own per-format folder (today just `import/obj/objimporter.{h,cpp}`, the single tinyobjloader TU — it triangulates, de-indexes unique `Vertex`es, generates smooth normals when the file lacks them, groups faces by material, and records `Kd` as base color), and is dispatched by file extension through `ImporterRegistry` (`import/importerregistry.{h,cpp}`). The registry is built from **one explicit list in its constructor** (`m_importers.push_back(std::make_unique<ObjImporter>())`, mirroring the `SHADER_SOURCES` list in CMake). So **adding a format is: implement `MeshImporter` under a new `import/<fmt>/`, add one `push_back` to the registry, and add the files + the `src/viewport/import/<fmt>` include dir to `CMakeLists.txt`** — nothing else changes. A mesh's texture is expressed as a `TextureSource` — *either* a resolved external file path (OBJ's `map_Kd`) *or* embedded encoded image bytes (e.g. a texture packed into a `.glb`) — so the IR already spans external and embedded sources; importers never decode.

Image decoding is deliberately **not** in the Qt-free core. The Qt-facing `ModelImportService` (`viewport/modelimportservice.{h,cpp}`) owns the orchestration: it looks up the importer (`ImporterRegistry::forPath`), runs `load()`, `QImage`-decodes the meshes' `TextureSource`s (from path *or* embedded bytes) into tightly-packed RGBA8, and calls `VulkanRenderer::addModel(ModelData)` — keeping the renderer free of any image-codec dependency while supporting every format Qt's image plugins do. **`decodeModelTextures` (shared by the OBJ and figure paths) decodes per unique SOURCE, not per mesh**: figure zones commonly reference the same atlas files (face/lips/ears share the face maps; torso/arms/legs the body maps), so each unique file is decoded ONCE — across cores via `parallelFor` (QImage is reentrant) — into a shared, immutable `DecodedImage` (`import/modeldata.h`) that every referencing mesh points at (`MeshData::diffuseImage` etc., `shared_ptr`); the GPU layer keys its uploads on the image's identity (`TextureUploadCache` in `scene/mesh.cpp`), so a shared image is also **uploaded once per model** (one staging copy + mip chain instead of per zone — this decode/upload dedup + parallelism cut a character import to a fraction of its serial time). Decodes are **resolution-capped** (`kMaxTextureSize`, 4096): characters commonly ship 8192² bump/roughness maps that cost 4× a 4K map at every stage (decode, fill, staging, mips, ~341 MB VRAM each) for detail the viewport can't resolve — `readCapped` folds the downscale into the decode via `QImageReader::setScaledSize` (a fast DCT-scaled decode for JPEG). Promote the cap to a Preference if a full-res close-up use case appears. It also **bakes any opacity (cutout) mask into the diffuse map's alpha channel**: the mask (a lash/brow card's shape, an older figure's eye-shell fade) is grayscale-decoded, rescaled to the diffuse dimensions, and written into `.a` — the bake COPIES the diffuse first, so each unique (diffuse, mask) pair gets its own shared image while unmasked users keep the pristine decode; `mesh.frag` computes `alpha = pushOpacity × diffuseTexel.a` (a no-op for unmasked textures, whose alpha is 1). A successful bake sets `MeshData::hasOpacityMask`, which `Mesh::isTransparent()` honours so masked meshes reach the alpha-blended pass even at scalar opacity 1 (a lash card's scalar is 1 — its shape exists only in the mask). And it **gutter-fills** each unique decoded image once (`import/texturegutters.{h,cpp}`, Qt-free): it rasterizes the **union of every user-mesh's UV triangles** into a coverage mask (a shared atlas must keep all its users' islands intact) and floods the unused atlas background with colours dilated from the islands (a pull-push fill across all four RGBA channels — baked alpha included — diffuse and normal/bump alike; the bake runs first so the mask gets the same seam treatment). The coverage raster has three defenses against pathological content, each learned from a real character: triangles identical in (quantized, wrap-folded) UV space are **deduplicated** before rasterizing (fibermesh strands — a 150k-triangle brow follower — map thousands of strands onto one UV strip; re-marking it per strand cost ~3 s per map), a mesh whose UVs span **multiple tiles** skips the fill entirely (a wrapping material samples its whole texture — no background to fill — and its tile-spanning triangles clamp to full-image raster walks), and the per-triangle walk is a **scanline** (per row, each edge's interval bound is linear in y) so cost tracks covered area + bbox height, never bbox area (long thin diagonal lash-card triangles otherwise walk millions of background texels). Without this, the GPU-built mip chain averages the (typically white) atlas background through every UV seam, which shows as bright seam lines at viewing distance; covered texels are untouched, so close-up rendering is unchanged. Keep this behind the decode choke point — any new import path that bypasses `decodeModelTextures` reintroduces the seams (and the per-zone duplication). The full chain is `MenuManager` (File → Import → `.OBJ`, a `QFileDialog`) → `ViewportWidget::importObj` → `VulkanWindow::importObj` (queues the path if the renderer isn't built yet — it's created lazily on first expose) → `ModelImportService::importInto` → `MeshImporter::load` → `VulkanRenderer::addModel` → `Scene::addModel`. `main.cpp` also feeds any `.obj` on the command line through `ViewportWidget::importObj` (drag-onto-exe / "open with"), which is why the queue-until-ready step matters. Imports run on the GUI thread between frames; the batched upload blocks briefly on its single submit but touches no in-flight state, so the next recorded frame just picks the new model up. Because that work is synchronous and can still be slow (large meshes, many textures), `ModelImportService` drives a modal staged `QProgressDialog` (read → per-mesh texture decode → GPU upload) — a `showProgress` flag gates it: interactive imports pass `true`, but the startup/command-line drain (called from inside `initializeVulkan()`/`exposeEvent()`) passes `false`, because a modal dialog's `processEvents()` could re-enter the expose/init path. The progress UI lives only in this Qt layer; the importers and renderer core stay Qt-free. **The File → Import menu is deliberately *not* registry-driven** — it lists all 10 formats as hardcoded entries in `menumanager.cpp` (alphabetical), with `.OBJ` (→ `importObjFile`) and **`.DUF (DUF File)`** (→ `importFigureFile`, the character-figure entry) wired and the rest disabled placeholders, so enabling a newly-added importer means flipping its menu entry from disabled to a real `QFileDialog`+import connect there. **Not yet:** non-diffuse PBR maps (normal/metal/rough — OBJ doesn't natively carry them), and the other 8 mesh Import formats are still disabled placeholders.

**Native figure importer** (`import/figure/`): imports rigged, morphable character figures from their **native scene format** — a gzip-compressed-JSON preset (`.duf`) that references geometry/rig/skin/morph/UV data files (`.dsf`) across a content folder. This is a much bigger importer than a mesh format (a figure is geometry + material zones + skeleton + skin weights + morphs), so it does **not** use the static `MeshImporter`/`ImporterRegistry` path (which returns `ModelData` and needs no external context) — it has its own rich IR (`FigureData`/`FigureMesh`/`FigureMaterial` in `figuredata.h`) and its own loader that needs the content-root folders to resolve cross-file URIs. **Legal/naming:** per the standing no-brand rule, no product or figure-line names appear anywhere in this code — and they don't need to: the format is self-describing, so **one figure-agnostic reader handles every figure family** (geometry, bones, weights, morphs, materials all come out of the files) — verified importing and rendering all seven target figure families (male & female base figures across several generations, plus a unified newer figure), including textured, morphed character presets. Qt-free layers, bottom-up:
- `figuredocument.{h,cpp}` — loads one file: read → gzip-sniff (`1f 8b`) → inflate (miniz) → parse (nlohmann). The single miniz-consuming TU.
- `uriresolver.{h,cpp}` — resolves the URL-encoded, root-relative cross-file URIs (`/data/…#id`, `/Runtime/…`) against the content roots (first existing wins; the exact-case path first, then a per-component case-insensitive fallback for case-sensitive filesystems, so Linux/macOS resolve the mixed-case URIs that NTFS absorbs for free), and **caches** parsed docs so a shared base file isn't re-inflated per reference.
- `geometryparser` / `uvparser` / `materialparser` — parse the base `.dsf` geometry (quads→tris, grouped by material zone), the external UV set (with per-corner **seam overrides**, so the mesh splits at UV seams; whole-surface smooth normals keep zone boundaries seamless), and the preset's physically-based materials (base color + texture maps — referenced either as a direct `image_file` path or, in newer generations, an `image` index into `image_library`). **Specular is interpreted from the material's LOBES, never one channel**: skin materials disable the glossy lobe (`Glossy Layered Weight` 0, its roughness left at 0) and author the real response in **Dual Lobe Specular** — broad lobe roughnesses (~0.6–1.0) blended by the lobe ratio, and a reflectivity ~0.3 that IS real skin's F0 (source convention F0 = 0.08 × reflectivity; 0.5 = the standard 4% dielectric). `materialparser`'s ladder (dual lobe when enabled + weighted → glossy lobe [`max(Glossy Roughness, 1 − Glossiness)`, the pair being two dials for one quantity] → struct defaults) yields an effective **roughness** plus a **specularWeight** (lobe weight × reflectivity/0.5, an F0 multiplier — folded in `foldSpecWeight`, which discounts map-carried weight/reflectivity channels by an assumed dark-mask average (the maps aren't sampled at import, and the dialed scalar is often >1 as the map's multiplier) and caps the result at 1 = the standard 4% dielectric; skin lands ~0.3–0.8 → 1–3% F0) and reads `Metallic Weight`; naively reading `Glossy Roughness` took the *disabled* lobe's 0 and rendered skin mirror-smooth — wet plastic under image-based specular, while an eye cornea (glossy lobe at its defaults) correctly stays mirror-smooth so the catchlight survives. Transparency for the eye's clear shells is keyed on a strong **Refraction Weight** (not a "no-map + low-roughness" heuristic, which wrongly turned some figures' untextured skin invisible) — and, for **older generations that predate that shader**, on the format's CORE top-level `transparency` channel (UI name "Opacity Strength"; the value IS the opacity, 0 = invisible): without reading it, an older base figure's cornea/moisture rendered as opaque white balls over the eyes. Either channel may also carry an **opacity (cutout) image mask** — lash/brow cards, the older moisture shells — captured as `opacityImageUri` and baked into the diffuse map's **alpha channel** by the decode layer (see the import-subsystem notes), so masked surfaces render with their real shapes. **Channel-value convention:** `current_value` is the *dialed* value and always wins over `value` (only the channel default) — for scalars *and* colours alike. Reading `value` for colours once rendered every zone with a 75%-grey default tint (textures too dark) and drew black-dialed pupils as bright grey/white dots in the eyes.
- `nodeparser` / `skinparser` — the skeleton (bone hierarchy + rest transforms from `node_library`) and the per-vertex top-4 skin weights (from the `SkinBinding` modifier), for GPU skinning.
- `morphresolver` / `morphparser` — the character's shape: `morphresolver` evaluates the preset's dialed channels through their **channel-driver formulas** (control → driven morphs); `morphparser` reads each reached morph's sparse deltas, baked into the base vertices at import.
- `correctiveparser.{h,cpp}` — detects + parses a **pose corrective** (joint-driven corrective morph) from a modifier: confirms it's rotation-driven, translates its `push`/`mult`/`spline_tcb` formula into the engine's stack-program IR (`PoseCorrective` in `modeldata.h`), and folds its character/enable gates to constants (dropping any a gate switched off). See the correctives paragraph below.
- `subdivision.{h,cpp}` — **Catmull-Clark** subdivision of the base cage into a smoother render mesh (positions smooth; UVs per-corner + skin weights refined linearly), then assembled per zone like the un-subdivided path. Also exposes `subdivideDeltaField` to carry a corrective's sparse deltas onto the subdivided cage (Catmull-Clark being linear). See the subdivision paragraph below.
- `figureimporter.{h,cpp}` — orchestrates: preset `.duf` → find the figure node's `geometries[0].url` → resolve+load the base `.dsf` → parse geometry → **bake dialed morphs** → parse skeleton + skin weights → **discover pose correctives** → resolve+parse the UV set → **subdivide the cage** (and each corrective's deltas) → assemble per-zone meshes (with joint weights) → attach each zone's resolved material → `FigureData` (meshes + skeleton + weights + correctives).

The Qt-facing `FigureImportService` (`viewport/figureimportservice.{h,cpp}`, the figure analogue of `ModelImportService`) resolves the **content-root folder(s)** the preset's `/data/…#id` URIs resolve against — **auto-detected** by walking up from the imported file to the ancestor containing `data/`, **unioned with any user-configured roots** (`Constants::PREF_FIGURE_CONTENT_ROOTS`, a newline-separated path list in Preferences), auto-detected first (most authoritative for a self-contained library) then configured. This matters because content is commonly split: a figure browsed from a **presets-only folder** (`.duf`s with no co-located `data/`) has *no* auto-detectable root, so without the configured fallback its geometry/morphs/skin/UVs (all under `data/`) can't be found and **every** figure fails with "cannot resolve base geometry" — the configured roots are what make that case work. It then runs `FigureImporter`, converts `FigureData`→`ModelData` applying the **cm→world unit scale (÷100)** so a ~180 cm figure lands at grid scale, decodes textures via the shared `ModelImportService::decodeModelTextures` (decode-once shared images — see the import-subsystem notes), and uploads through the **existing lit mesh pipeline** (`addModel`). Routing mirrors OBJ: `ViewportWidget::importFigure` → `VulkanWindow::importFigure` (queues until the renderer exists) → the service; File → Import → **`.DUF (DUF File)`** (the character-figure entry in the alphabetical format list, `*.duf`/`*.dsf` filter), command-line/"open-with" `.duf`/`.dsf`, and **double-clicking a figure asset in the Asset Manager grid** (`AssetManagerWidget::importFigureRequested` → `ViewportWidget::importFigure`, the figure analogue of the `.obj` → `importModelRequested` route) all route here. **Failure feedback (interactive path only, `showProgress`):** `importInto` classifies the failure and responds in kind. A `.duf` that isn't a figure (pose/material/light presets share the extension and all appear in the grid) throws "no geometry reference found" → a `QMessageBox` ("this may be a pose/material preset rather than a figure…"). A real figure whose `data/` library isn't on any known root (empty roots, or a resolve error) is the **recoverable** case: a **"Locate Content Folder…"** prompt → a folder picker → the chosen root is persisted to `PREF_FIGURE_CONTENT_ROOTS` and the import is **retried once** with it folded in (a single-shot `for (attempt < 2)` loop), so the fix is one-time and remembered. The startup/command-line drain (`showProgress=false`) stays dialog-free (returns false silently) to avoid re-entering the expose path. The actual per-attempt work lives in a file-local `runFigureImport()` that `importInto` calls inside that loop. Materials also **merge the `material_library` base** each scene material extends by `url` (`#id`): a scene material only *overrides* channels, so roughness and the transparency-defining channels (which live on the base) are read from the merge — essential for the eye's clear shells. **Current state:** a figure renders textured in bind pose with per-zone roughness-driven specular, cheap **subsurface skin shading** (wrap-lighting + a warm subsurface band, in `mesh.frag`), alpha-blended transparency for the eye's clear shells (cornea/moisture — detected via the material's `Refraction Weight` channel read from the merged base, so the iris shows through), tangent-space **normal-map** support (screen-space cotangent frame — no vertex tangents), and grayscale **bump** maps applied as a mip-stable **texture-space central-difference** perturbation (height sampled at `textureSize`-derived texel offsets — this replaced an earlier screen-space version that was too noisy on the UDIM maps), which is what gives the base skin its surface grain. **Phase 3 (skeleton + skinning) is done and the figure is posable:** `nodeparser` builds the bone hierarchy from `node_library`, `skinparser` inverts the `SkinBinding` modifier into per-base-vertex top-4 weights, `assembleFigureMeshes` attaches those to each render vertex, and `FigureImportService` hands the renderer a `ModelData` with a skeleton (`ModelBone` list). At the GPU layer every `Model` carries a joint-matrix storage buffer (see the mesh-pipeline notes) and a runtime skeleton; `Model::setBoneRotation(name, eulerDegrees)` poses a joint and recomputes the skin matrices. **Phase 2 (character-identity morphs) is done:** `morphresolver` walks the preset's dialed channels through their **channel-driver formulas** — a character dials a *control* (e.g. `CTRL<character> = 1`) whose linear `push`/`mult` formulas drive the real head/body shape morphs (`FHM…`/`FBM…`) — and `morphparser` reads each reached morph's sparse deltas, which the importer **bakes into the base vertices** (`position += weight·delta`) before assembly, so the generic base becomes the specific character (verified on real character presets: face + body shape). **Joint-center adjustment is part of this:** the same full-body/head morph modifiers also carry driver formulas whose *output* is a bone's `center_point/{x,y,z}` (a `FBM<character>` typically has hundreds — e.g. `hip.center_point.y += FBM<character>.value · coeff`), so the rig follows the character's new proportions. `morphresolver` returns these as a per-bone `JointCenterOffsets` map (routed out of the same formula walk that resolves morph weights — a bone `center_point` is *not* a morph channel to propagate), and `figureimporter` adds each offset to the matching `FigureBone::origin` right after `parseSkeleton` — before skin-weight parse, corrective discovery, subdivision, and assembly — in the same native-cm space as `origin` (the cm→world × `figureScale` in `toModelData` then scales mesh and skeleton together). Without this, a *base-figure* rig sits inside a *morphed* mesh: posed limbs pivot at the wrong places and the joint overlay floats off the body. `end_point`/`orientation` outputs are skipped — the bind is translation-only and orientation is read straight from the node, so they don't affect skinning. Verified: an unmorphed base figure shifts 0 bones; a strongly-stylized character shifts ~169/171 (max ~6.4 cm). **Posing is anatomically correct:** a bone's rest transform stays translation-only (the orientation cancels at rest — `T·OR·OR⁻¹`), and `setBoneRotation` applies the rotation in the joint's oriented frame (`localBind · OR · R(euler, rotation_order) · OR⁻¹`), so an elbow/knee/shoulder bends about its true axes (verified). **Joint rotation limits are enforced:** each bone's `rotation/{x,y,z}` channel carries a `min`/`max` range (degrees) and a `clamped` flag (the format's per-channel "use limits") — the joint's anatomical range of motion (a knee ≈ x∈[-11°,155°], the neck ≈ x∈[-30°,25°]). `nodeparser` reads these into `FigureBone` (matching axis by channel *id*, not array position, since the array is ordered per `rotation_order`), they flow through `ModelBone`→`GpuBone`, and `Model::clampBoneEuler()` — called at the top of `applyBoneEuler()` and in the `applyPose()` loop, the two points every posing path (free-drag, gizmo, pose load, undo) funnels through — clamps each *limited* axis to `[min,max]` in place (so accumulated drags stop cleanly at the limit and saved/queried poses reflect the clamped angle). The format carries **two distinct constraints** and `nodeparser` honours both: `clamped` (move within [min,max]) and **`locked`** (cannot be posed at all — enforced as a hard [0,0] clamp). `locked` is how figures forbid anatomically impossible motion: a mid-limb twist bone (which exists only to spread axial twist across the skin) locks its two bend axes so the limb can never fold where there is no joint — beware that these bones are *not* reliably named "twist" (in several generations the mid-forearm bone is named like a wrist joint, with the real wrist named like a hand), which is why the geometric name-based twist-lock fallback in `figureimporter` missed it; that heuristic now defers to any format-locked axis and remains only for old generations that predate the `locked` flag. Axes with neither flag, and models without a skeleton (OBJ), stay unconstrained. Verified: a base figure reports 399 limited axes across 171 bones, a 300° request on the knee clamps to 155°, on the neck to 25°, and a pose file demanding a 60°/60° bend on the mid-forearm joint's locked axes leaves the forearm straight while its twist axis stays free in its authored range. **Not yet:** limits aren't surfaced in the UI (no visual range indicator on the gizmo), and there's no global "use limits off" override; morph-driven limit *adjustments* (a formula driving `rotation/x?min`) aren't applied — the base node limits are used as-is. **Interactive posing UI:** the **skeleton overlay is hidden by default** — the rotate gizmo (below) is the sole visual affordance, so the character isn't cluttered with a bone cage. `Scene::record` still owns a coloured line list drawn through a dedicated line pipeline (over the mesh, depth test off), but only emits the joint→parent segments when `m_showSkeleton` is on (toggled by **View → Show Skeleton** and the checkable bone-icon **Skeleton** button in the viewport strip — the two stay in sync through `ViewportWidget::skeletonVisibilityChanged`, and the state lives in `VulkanWindow::m_showSkeleton`, remembered across the lazy renderer build like the shade mode); the gizmo rings are emitted **independently of that flag**, whenever a joint is selected. Crucially, **picking is independent of what's drawn** — `Scene::selectBoneAt` projects every bone to screen and hit-tests within a pixel radius regardless of overlay visibility — so joints stay clickable even though invisible. In `VulkanWindow`, a **left press that lands on a joint** (nearest projected bone within a pixel radius — `Scene::selectBoneAt`) selects it and enters posing, bringing up the gizmo, so that drag **rotates the joint** (`Scene::nudgeSelectedBone` → `Model::setBoneRotation` in the oriented frame) instead of orbiting the camera; a left press on empty space orbits (even while a joint stays selected — `selectBoneAt` returns -1 on a miss but keeps the selection). `setBoneRotation(name, eulerDegrees)` remains the underlying primitive. A **rotate gizmo** draws three axis rings around the selected joint (X/Y/Z = red/green/blue) in the joint's own rotation frame (`Model::selectedBoneFrame` = `parentGlobal·localBind·orient`, so each ring maps to one Euler channel — including twist, which free-drag couldn't reach): a left-press that grabs a ring (`Scene::gizmoAxisAt`) enters an **axis-constrained** rotate where the drag's swept screen-angle about the joint drives that one channel (`Scene::rotateGizmo`), while a press on the joint itself still free-rotates. **Undo/redo is unified** (`VulkanWindow::undo/redo`): ONE chronological stack of typed `UndoEntry`s holds both **pose edits** (each committed drag pushes the pre-edit pose via `Scene::capturePose`/`applyPose`, the pose save/load primitives; applying an undo re-runs correctives like any pose change) and **Environment-panel lighting edits** (the panel brackets every gesture — dial scrub/type-in via `DragNumberBox`'s `editingStarted/editingFinished` signals, restore buttons, tonemap toggle, restore-all, depth-counted so composite edits register once — and calls `registerLightingUndo` with the pre-edit `LightingSettings`; undoing one re-applies the dials and emits `lightingRestored` → `ViewportWidget` → the panel, which syncs its widgets signals-blocked). It's driven by the **Edit → Undo/Redo actions** (`QKeySequence::Undo/Redo` — these window-level shortcuts are what make `Ctrl+Z` work while the panel has focus; focused text fields still keep their own Ctrl+Z via ShortcutOverride) with `VulkanWindow::keyPressEvent` as the in-viewport fallback. **Driven figure scale is applied:** `morphresolver` accumulates the preset's `scale/general` driver-formula contributions into `FigureData::figureScale`, which `FigureImportService` folds into the cm→world scale (so a taller/shorter character lands at the right height, mesh and skeleton together). **Only formulas targeting the FIGURE root node count** (the geometry-bearing scene node, matched by asset-url fragment): bone-targeted `scale/general` outputs are *propagating-scale rigs* — e.g. a head-scale control driving ~80 per-bone channels — and summing them into the figure scale once imported a teen character at 3× size (78 × the head dial stacked on top of the real figure dial). Per-bone scale isn't modeled (the bind is translation-only), so those outputs are dropped, not misapplied. Verified: the teen figure resolves 0.91 (its −0.09 figure dial), an oldest-generation child preset 0.54 — both landing at correct heights. **Pose save/load is wired:** `Model::capturePose()`/`applyPose()` (bind pose + named Euler rotations) round-trip through `Scene::savePose/loadPose` (a plain-text `.pose` file, one `name rx ry rz` line per posed joint — safe because figure bone names are space-free tokens), forwarded out through `VulkanRenderer`→`VulkanWindow`→`ViewportWidget`; File → **Save Pose… / Load Pose…** drive it, and a `.pose` path on the command line / "open-with" applies onto the imported figure (queued behind it like the figure itself). **Pose correctives are done:** joint-driven corrective morphs that fire as a function of bend angle to fix the mesh crumpling ("candy-wrapper") at deep elbow/knee/shoulder/hip bends. They aren't listed by the preset, so `figureimporter` discovers them **structurally** — a morph whose driver formula is driven by a joint `rotation/{x,y,z}` channel — scanning the corrective/flexion folders (plus each dialed character's own morph folder) under `<figure>/Morphs`; this is figure-generation-agnostic (the corrective files are named differently from one generation to the next, but the structure is identical — detection is never keyed on file/brand names). **Point-release figure generations inherit the previous generation's correctives via a SIBLING-BASE fallback**: a variant figure whose own Morphs tree has no corrective packs (its tree holds only head/FACS content — the source app links it to the earlier generation through its content database) gets the packs of a sibling figure directory whose base file's digit-stripped name matches AND whose base cage has the identical vertex count — morph-compatible by construction, so the delta indices land verbatim; only attempted when the own tree is empty, so same-generation figures never pay the sibling parse. **Weight fidelity is exact to the source app** (verified against the authored files): only formulas whose OUTPUT is the modifier's own `?value` channel contribute to its weight (vendor character JCM files bundle dozens of morph-driven joint-center/orientation adjustment formulas in the same modifier — summing those produced garbage), gate urls are URL-DECODED before matching dialed morph ids (vendor ids contain spaces), and the driven weight is CLAMPED to the morph channel's authored `min/max` — load-bearing for linear-ramp drivers: a knee-EXTENSION flexion is authored as `rotation/x × -1/11` and relies on the clamp to stay 0 through the 155° of flexion (unclamped it hit **-14** and cratered every deeply-bent thigh). `POSESTUDIO_DUMP_CORRECTIVES=1` prints each active corrective + weight whenever a pose settles. The scan is **parallel and pre-filtered** for import speed: candidate files load (read + gzip-inflate) across cores in bounded chunks, and a file whose inflated text lacks the literal `?rotation/` is skipped before the (dominant) JSON DOM parse — provably safe, since `correctiveparser`'s driver detection requires that exact literal form, and the dialed-morph folders hold hundreds of plain shape morphs that can never pass it; only the cheap `parseCorrective` walk stays serial (its gate resolution shares the non-thread-safe resolver cache). The dialed identity-morph documents are likewise **prefetched in parallel** (`UriResolver::prefetchDocuments`) before the bake loop. `correctiveparser` translates each driver formula (the `push`/`mult`/`spline_tcb` vocabulary the base correctives actually use) into a small stack-program IR (`CorrectiveOp`/`CorrectiveFormula`/`PoseCorrective` in `modeldata.h`), **folding the character/enable gates (the mult-stage drivers) to constants at import** — resolved to the dialed weight if the preset dials that channel, else the channel's own default `value` — so a non-loaded character's correctives (gate → 0) are dropped at import while a figure's default-on "base joint correctives" master toggle (default 1) keeps the base set live. At the engine, each `Model` keeps the affected meshes' base (uncorrected) vertices and, per corrective, the render vertices its base-vertex deltas map onto (built once from each mesh's `baseVertex` array); `refreshCorrectives()` re-evaluates every corrective's weight from the current pose (a Catmull-Rom spline through the driver knots, clamped per-segment to avoid overshoot × the folded gate) and, if any changed, re-morphs the affected meshes on the CPU (base + Σ weight·delta) and re-uploads them (a `vkDeviceWaitIdle` first, since an in-flight frame may reference the old buffers) — the GPU skinning then bends the *corrected* bind mesh. It runs immediately on `setBoneRotation`/`applyPose` and on interactive **drag release** (`Scene::finalizePose`, deferred during the drag since re-uploading geometry mid-drag would stutter). Verified end-to-end on two figure families (113 and 97 correctives discovered): deeply-bent elbows/knees fire the right correctives (22 / 8 active respectively) and deform cleanly. **Catmull-Clark subdivision is done** (`import/figure/subdivision.{h,cpp}`, wired in `figureimporter` at `kSubdivisionLevels = 1`): the low-res base cage is smoothed into the render mesh so limbs/torso/face read round rather than faceted. Positions follow the smooth Catmull-Clark rules on the watertight cage (face/edge/vertex points; boundary edges use the cubic B-spline rule); UVs are kept **per polygon corner** and refined *linearly* (each sub-face's corners get their parent face's corner UVs averaged), so texture seams split exactly as before; skin weights are refined by blending (edge/face points average their contributors' top-4, vertex points keep theirs). The subdivided cage is then run through the *same* de-index/seam-split/smooth-normal assembly as the base path, so `Scene`/`Model`/skinning/correctives are all unchanged — they just see ~3–4× the vertices (a ~16.5k base cage → ~56k affected render verts at level 1). **The corrective machinery needed no change** because Catmull-Clark is a *linear* operator: each corrective's sparse base-cage delta field is carried onto the subdivided cage by the same stencils (`subdivideDeltaField`) at import, so the runtime re-morph (`base + Σ weight·delta`) works directly on the dense mesh. Verified: the subdivided figure renders smoother, textures + skinning intact, and the base correctives still fire (22/113 active on a bent-elbow/knee pose, re-morphing the dense zones). Cost: extra import time (subdivision + subdividing the delta fields — the latter parallelized across cores via `parallelFor`, one independent full-mesh stencil pass per corrective) and a heavier re-upload on pose-settle. **Post-load follower addons are merged:** a character preset can declare *follower* figures to be loaded after it — a `scene_post_load_script` extra block whose `PostLoadAddons` settings list wearable `.duf`s plus a materials preset each. This is how an entire figure generation attaches its **eyelashes**, and how stylized characters ship **replacement anatomy** (e.g. an anime character whose preset dials every standard eye surface to cutout 0 and supplies separate cartoon eyeball/eye-socket/brow/lash figures — without addon support she imported with empty eye sockets). `figureimporter` parses the block (`findPostLoadAddons` — the preset key under `Presets` is NOT fixed: usually `Mat` but e.g. `Brow Mat` for one vendor's brows, so every entry carrying a `PresetFile` is collected and applied; the appliers no-op on non-material documents), loads each addon through the same `loadFigureFile` pipeline (they're self-describing wearable figures; recursion is one level — addons can't pull addons), applies its presets, **shape-follows** it, and merges it (`mergeAddonFigure`): skeletons merge by bone NAME (shared bones resolve to the parent's so the follower tracks pose; follower-only bones — e.g. anime-eye lens joints — are appended), and mesh `baseVertex` indices are offset out of the parent correctives' base-vertex space. **The fit model has three load-bearing rules, each learned from real content:** (1) ordinary followers are authored against the BASE figure and must be **shape-follow projected** (`followParentShape`): each render vertex gets the morph delta of the nearest parent base-cage vertex (nearest-vertex is fine — the cage is dense; off-surface strand tips inherit their root's delta) — without this, fibermesh eyebrows float in front of a morphed forehead. (2) An addon whose geometry declares a **populated graft** (non-empty `hidden_polys`/`vertex_pairs` — e.g. the anime character's custom eyeballs) is vendor-fitted in place and must NOT be projected (double-shifts off the face); note a *generic* follower still carries an *empty* `graft` object, which doesn't count — and never re-fit by snapping to parent joints either: follower rigs deliberately place bones away from the parent's (a flat anime eye pivots from *deep inside the head* so it can slide across the face like a curved screen). (3) Projection deltas are sampled **only from visible-zone cage vertices**: a stylized preset hides the stock surfaces its addons replace AND its morph stashes that hidden geometry (shrinks the stock eyeballs into the head), so followers sampling near hidden zones would inherit garbage deltas. Addon failures skip just that addon, never the figure. Materials presets come in **two forms** and both are applied: ordinary `scene.materials` docs (`applySceneMaterials`, shared with the main path) and **`preset_hierarchical_material`** docs (`applyAnimationMaterials`) whose values ride in single-key `scene.animations` tracks (`<node>#materials/<zone>:?<property>` → `keys[0][1]` — diffuse color/map, Cutout Opacity, Refraction Weight, Glossy Roughness, Normal/Bump maps; the anime-eye "lens over iris card" only turns transparent through this form). Verified: the anime character renders her cartoon irises (23 zones, was 16) plus followed brows, a standard character gains her previously-missing lashes (18 zones, was 16) with eyes/scale unchanged, and a realistic character's fibermesh eyebrows land on her morphed brow ridge instead of floating in front of the base-shape forehead. **Not yet:** the *identity*-morph driver-formula evaluator (`morphresolver`) still approximates spline/other ops as no-ops (the corrective path has its own real spline evaluator); the gizmo's axis-drag isn't gimbal-exact (it drives one Euler channel) and HDRI *selection* isn't on the undo stack (only the lighting dials and poses are — an HDRI switch is a re-bake, not a cheap state re-apply); addon **graft** metadata (`hidden_polys` — parent polygons a graft is meant to hide) isn't processed (so far redundant: these presets also dial the replaced surfaces invisible); generic base-authored followers (clothing fitted to an arbitrary character) would need real auto-fit projection, and a posed follower rotates about the *parent's* joint pivots, not its own. The core figure pipeline — import, character morphs, materials, rig, skinning, correctives, subdivision, follower addons, and the posing UI — is complete.

**Full-body IK (FBIK)** (`scene/ik/`, Qt-free: std + GLM): **Ctrl+left-drag a joint** IK-drags it — the grabbed joint follows the cursor in a camera-parallel plane through its grab point while the whole body follows anatomically, with the **ground contacts as the anchors** (never the hip): joints whose world height is under `kIkContactHeight` (meshik.cpp; feet/toes standing, knees kneeling) are detected at drag start and become **pins** the solve must keep planted (contacts within a LIMB'S LENGTH of the effector — `kEffectorLiftReach`, tree-path metric, not hop count — are released: dragging a foot lifts the foot and its entire toe subtree instead of fighting its own toe-tip pins, a shin drag frees the foot below it, and a hip drag keeps both feet; hop rules broke both ways on real rigs — tiny 2cm trunk bones put a thigh 2 hops from the hip while small-toe tips sit 4 hops from the ankle), while the **pelvis root FLOATS**, held by the planted limbs, its solved displacement absorbed as root pose translation (**the FBIK root is `IkRig::rootNode()` — the first multi-child DESCENDANT of the anatomical root, never the anatomical root itself**: real figures root at an origin-level FIGURE NODE with the hip as its lone child a meter up, and that virtual-ancestor chain is excluded from the rig WHOLESALE — no graph edge, no contact eligibility, no balance mass. The figure node sits ON the floor, so contact detection planted it and pinned the whole figure to the origin through a phantom hip→origin "bone"; the solver's per-tick compromise between that pin and the real leg pins ratcheted the hip floorward ~3mm/tick — the "single gentle pull sinks/floats the figure" bug — while every root mechanism (leash, root prior, balance target) aimed at the wrong node. Found only by dumping a real figure's skeleton into the loop harness; the synthetic hip-rooted rig couldn't reproduce it); with nothing planted (airborne figure) the root is pinned in place, and **dragging the hip itself** makes the root a pin ON the drag target (the one joint FBIK places directly), so the feet re-plant around a dropping pelvis — a crouch — with balance skipped (the user is driving the pelvis explicitly). Plain drags remain FK — nothing about the existing posing UI changed. Module layout: `skeletongraph.{h,cpp}` (the joints as an UNDIRECTED graph with BFS re-rooting; the rig roots it at the pelvis so **traversal order equals hierarchy order**), `fabriksolver.{h,cpp}` (multi-chain FABRIK: forward/backward passes with sub-base centroid branching, multiple pinned effectors, per-segment constraints), `ikconstraints.{h,cpp}` (position-level joint limits DERIVED from each figure's own authored per-axis Euler ranges: the oriented axis most parallel to the child segment is twist, the others swing — one free swing axis ⇒ **1-DoF hinge** (knees/elbows), two ⇒ **asymmetric cone**, swing decomposed onto the two oriented axes and clamped per-axis to the real signed ranges — a symmetric aperture let limbs fold the impossible way), `balancecontroller.{h,cpp}` (**CoM auto-balance**: biomechanical segment masses from tolerant bone-name classes — same-class same-side bones split a share so a Bend+Twist pair isn't double-counted — CoM at segment midpoints, support polygon = convex hull of the planted contacts in XZ, and the correction that brings the CoM's ground projection back inside, applied as a soft pelvis effector; degenerate 1–2-point hulls get a foot-area slack radius so point-feet don't demand exact-line balance), `ikrig.{h,cpp}` (per-figure orchestration: contacts → pins/hull → solve → balance loop), `ikmath.{h,cpp}` (shortest-arc, signed angles, and `eulerFromMatrix` — the exact inverse of `eulerMatrix` for all six rotation orders, gimbal-guarded), and — outside `ik/` — `scene/meshik.cpp`, the Model-side ENGINE BOUNDARY (rig build, contact detection, drag/settle ticks with their governors, rotation extraction): the one file where the Model and the solver meet, kept separate from mesh.cpp so solver and engine work evolve independently. **Solver policies that are load-bearing** (each fixed a real failure — the first in-app test sent the figure FLYING OFF SCREEN, and every rule below traces to a bug found fixing that): constraint frames must be evaluated on the OWNING (parent) side, which is why the rig abandoned re-rooting the traversal at a contact — walking a limb inverted accumulates frames from the child side, skewed by each joint's own swing (the lower thigh inherited the knee's bend and "kinked" at a rigid twist joint); `shortestArc` is guarded on the CROSS length and the accumulated frames are renormalized (norm drift once made two IDENTICAL vectors' dot fall below an acos-guard, and the resulting `normalize(cross(v,v))` NaN was the fly-away: NaN skin matrices); edge lengths come from BIND data, never measured from entry positions (a directly-placed root arrives inconsistent); the **root's rotation is FROZEN** (frameSeed) — FBIK translates the pelvis but never rotates it (nothing anatomical limits a root, so the solver happily pitched a pelvis 110° through itself to absorb a crouch); the **straight-limb escape** (a collinear chain can never decide a bend direction) is an incremental error-scaled push into a one-sided hinge's deep side / an asymmetric cone's dominant axis, living ONLY in the restoration chains and **triple-gated**: stall (no round progress), `kKickErrorFloor` ≈ 2.5cm (converged poses carry mm-noise that also reads as "stalled" — kicking on it ratcheted held poses deeper every solve), and — critically — **FOLD NEED** (the chain's target lies well inside its reach, < 97% of chain length, so a bend is geometrically required; error size alone is NOT a fold signal — a standing leg whose foot pin drifted a few cm has its target AT reach, and kicking it toward the thigh's dominant range side hoisted the knee of a planted leg during ordinary hand drags); **best-state keeping** at global and per-chain level (greedy constrained iteration wanders; only POST-iteration states qualify and at least one iteration always runs); and per-effector **restoration chains** — for pins AND the drag goal alike (single-chain FABRIK from each effector to its sub-base — the nearest branching ancestor, another effector, an INACTIVE ancestor (a caller-frozen base — restoring through one moved nodes the active mask promised untouched), or the root, never THROUGH an interior goal; the goal's own chain is what lets a straight arm fold its elbow to bring the hand inward). Each restoration chain that collapses (through its rigid twist-bone pass-throughs) to a classic TWO-BONE limb — mid = the FIRST deep-fold joint from the effector (≥120° dominant range — knees ~166°, elbows ~155°; a ~110° ankle or small wrist articulates slightly inside the lower segment instead), base = the next real joint above it (selecting the WIDEST joint instead broke arms whose shoulder out-ranges the elbow, and first-two-real gave metatarsal-pinned chains a degenerate ankle+knee pair that left hovering feet assist-less) — gets an **analytic two-bone seed** before its rounds: the mid joint is placed exactly on the two-sphere intersection circle and the constrained rounds then legalize it against the joint limits. **Which side of the base-to-goal axis the mid joint bulges to is the joint's FLEXION side** (the opposite of its `dominantBendTangent`, rotated into the chain's frame): the current knee's side is kept only while it IS that side. Seeding "nearest to the current mid joint" regardless cemented a blocked basin — a knee the clamp had left on its hyperextension/lateral side was re-seeded there every solve, the clamp cut the seed's 21° swing to its 12° of hyperextension-plus-play (`x∈[-11°,155°]`, `z∈[-5°,5°]`), the foot sat 7cm off its pin, and the thigh crept toward the fix at 0.2°/round (`IK_CHAIN_TRACE=<node>` prints a chain's per-round error and per-edge want/got/clamp angles — this is how it was found): every walk landing ended 5cm inside its stance and 1.5cm through the floor. A hinge-aware reach (solving the knee angle through the rest offset) was tried first and rejected — this figure's leg rests straight (1.3°), so it was a no-op that only perturbed the chaotic landscape. This killed the recurring extend-to-plant basin (a limb converging onto a near-full-extension target hard-stopped centimeters short — crouch feet lagging, a sustained hand pull gradually trading a planted foot away, strained releases stalling off their pins); it is purely exploratory — the per-chain best-state keeps the seed only when it lands the effector better. **The MOTION during a drag is engineered, not just the end pose** — the drag runs as a 60 Hz damped process, and every piece below exists because its absence produced a specific visible artifact: `VulkanWindow` re-issues the drag target on a ~60 Hz timer while the button is held (catch-up continues when the mouse stops — mouse-move events stop with it) and LOW-PASS FILTERS the raw cursor target ADAPTIVELY (`issueIkTarget`: alpha follows how far the smoothed target LAGS the raw one, clamped [0.30, 0.85] at 30/m of lag — retuned from [0.18, 0.85]/12 in the lag round for −14% tracking lag at moderate speeds; the harness's `[real] profile` phases now report lag mean/max and catch-up ticks, its `6c` phases drag the head, the chest, an EYE (promoted to the head) and a head with ±2mm cursor noise (`g_cursorNoise`) watching the dragged joint's own per-tick reversals, and the in-app bench's report carries the same oscillation metric (`osc`, the grabbed joint's accumulated reversal overlap per phase), and the lag round's REJECTED levers are recorded there: under-relaxation 0.65/0.8 (−3/−6% lag, breaks tremble+profile gates), solver trust region 0.10 and 16-20 iterations/tick (no lag gain, break gates), rotational prior 0.025 (no gain), a solver-shortfall compensator (the ~1.7cm residual a hand rests short of the cursor is CONSTRAINT-bound — position-level limits stop the chain slightly short of the Euler limits — so over-asking just jitters), and a 25-40mm catch-up floor ceiling (35→25 ticks on a flick, but the crouch's re-planting feet wander: the solver's own per-tick progress, not the floor, bounds catch-up); the remaining moderate-speed lag (~3.5cm at 0.45 m/s: filter ~1.1cm, relaxation ~1.4cm, constraint residual ~1cm) is the anti-tremble design's price — a user "responsiveness" preference scaling relaxation/filter/accel is the intended way to move that dial — near-still cursor = heavy smoothing, so pixel noise never reaches the solver, which AMPLIFIES it ~14×: ±2mm of noise shook joints by ±3cm, the "extreme trembling"; fast deliberate gesture = the filter opens and follows tightly, so smoothing costs almost no lag exactly when the user moves fast — the old fixed 0.35 charged ~40ms on flicks while passing ~2× the noise on precise holds. The faster-converging filter needed a symmetric BRAKE in the governor: the movement allowance may also SHRINK at most `kIkBrake`/tick, else a stopping cursor collapsed the tracking budget in one tick — a measured 23mm single-tick speed drop, a visible hitch). The solver runs only a FEW iterations per tick (`kIterationsPerTick` = 10, ikrig.cpp, with every solve passing `priorIterationNorm` = 6/10 so the per-iteration pose prior's per-SOLVE pull stays at its tuned strength — raising iterations unnormalized silently stiffens every prior and broke hover-healing; convergence is meant to happen ACROSS ticks; a large per-tick budget re-resolves the whole configuration every event and near-equal configurations flip with millimeter target changes). Per-event pose change is then rate-limited at three levels, each necessary (an internal basin switch otherwise lands as a SNAP in one event): the solver's positional trust region (`Settings::maxStepDisplacement`, 5cm/solve), a per-joint angular cap at extraction (`kIkMaxJointDeltaDeg`, 12°/event — positional caps alone amplify through rotation levers), and the world-space governor in `Model::dragIkTo` (meshik.cpp) — UNDER-RELAXATION (`kIkRelaxation` 0.5, damping period-2 configuration alternation) plus a movement cap PROPORTIONAL to the target's own motion (3×, floored at a gentle settle speed, capped at `kIkMaxWorldStep` 10cm; per-joint angular caps still COMPOUND down a chain, so the whole pose delta is scaled to fit) — the settle-speed floor is ERROR-SCALED (0.25 × the entry goal error, clamped [3mm, 12mm]: with goals far off — a crouch re-planting, a hover healing — catch-up flows at the full 12mm/tick, while a near-converged pose during a SLOW pull can only creep; the fixed 12mm floor let solver churn flow through whole slow drags as ~1cm idle-joint jerks), and each joint's applied delta additionally passes a REVERSAL-GATED micro-damp (`kIkMicroDampDeg` 0.15°: a delta OPPOSING the joint's previous applied delta — the loop's own tick-scale oscillation, which uniform under-relaxation attenuates but sustains — is scaled by e/(e+0.15°), killing sub-0.1° shimmer below perception; the gate must be the reversal, not the magnitude — magnitude-gating also shaved a raising arm's steady climb until the rotational prior's per-tick take-back overcame it and the hand visibly SANK mid-raise. Both governors have new tremble regression gates in the harness: worst idle-joint single-tick step and accumulated reversal-overlap oscillation, measured on slow and medium real-skeleton pulls). The whole allowance is additionally VELOCITY-SHAPED (`kIkAccel`/`kIkDecel`, with `Model::m_ikAppliedSpeed` as the state): it may grow at most 10mm/tick² over the previous tick's actually-applied speed — a brisk flick ramps up over several ticks like a real limb's spin-up instead of jumping to full rate in one (the profile harness measured a one-tick 0→19mm/tick jump pre-shaping) — and never exceeds the braking curve `sqrt(2·kIkDecel·goalError) + 3×targetDelta` toward the goals, so catch-up after the cursor stops decelerates smoothly into the pose instead of running at a constant rate and stopping flat; the tracking term keeps a MOVING cursor's pursuit unthrottled (the lag behind a live drag is meant to be consumed at speed). The release settle shares the shaping: it CONTINUES at the drag's speed at mouse-up and brakes into the plant, rather than popping to its fixed 2cm/tick rate. Tighter constants (6mm/2mm) were probed and rejected — they lagged pin corrections enough to push a crouch-push foot 3.6cm through the floor and re-perturbed the up-sweep; motion-profile gates (max single-tick speed increase/decrease of the effector on medium and fast real-skeleton pulls) now hold the shape. Finally the **settle-freeze** (`m_ikFrozen`, mesh.h): while the target stays within a 4mm stillness ball (CUMULATIVE drift from an anchor — a slowly CREEPING drag re-anchors and stays live, zero-mean noise doesn't), worst-goal-error minima are collected in 6-tick windows, and when a window stops improving on the last — AND the pins are decently planted (<5cm; freezing a stalled catch-up would lock feet in the air) — solving STOPS COMPLETELY until the cursor moves; a held pose is rock-still because no budget tuning survives sustained solving: configuration flip-flops consume whatever budget exists (this was learned four failed heuristics deep: error-proportional, per-tick-progress, and low-water-mark budgets all let the oscillation fund itself). **The figure can never be hoisted off its planted feet**: each pin carries a **reach leash** (`IkEffector::leashRadius`, set by the rig = the DRAG-START root-to-pin distance — a stance the figure provably held — with fractional path-sum headroom for bent-leg starts; the raw path-length SUM overcounts because the pelvis-to-socket offset is lateral, not collinear with the leg) and the solver projects the floating root into the intersection of those balls every iteration — pulling a hand skyward now extends the body and stops, instead of levitating the figure (a PINNED root is exempt: an explicit pelvis drag may lift the feet, that's user intent). The per-node **prior weights double as the stiffness model** (`m_priorWeights`, ikrig.h): weight grows with graph distance from the effector (dragged limb ~0.3x, trunk ~1.3x, far limbs 2.5x — natural recruitment order), EXCEPT pin-serving chains, which stay nearly prior-free — the prior pulls toward absolute START POSITIONS, and once the trunk leans, dragging a planted leg's joints toward where they used to be swings the limb off its pin — and the ROOT, which is the STIFFEST of all (5x) for limb drags: a person pulling a hand barely moves their pelvis, but the forward pass dragged the floating root a little toward every target, and the spine arched around the slid pelvis into a swayback "hip thrust" on gentle drags (explicit pelvis drags and balance corrections are effector-exempt). **Pins are the MOST PROXIMAL planted contact per limb only** (the ankle — a contact with no planted ancestor): pinning every toe/metatarsal joint individually made the solver bend the foot and curl the toes to hold their pins whenever the ankle shifted millimeters; with only the ankle pinned, foot and toes stay off the active set and ride rigidly (the support polygon still spans ALL contacts — toes give the real footprint). An explicit pelvis drag (a crouch) runs 3x the per-tick solver iterations — both legs folding in coordination need more than a limb drag. **Pin targets are GROUND-HEALING**: a contact hovering near its natural floor height is pinned AT bind height, not where it hangs (bounded — a kneeling knee or airborne pose keeps its height), the prior pose is height-shifted by the same amount (the stiff root prior otherwise anchored the hover), and the balance pelvis effector takes its Y from the prior (being an effector, it silently disabled the root prior and froze a hovering figure's descent); when NO contact is under the threshold, `Model::beginIkDrag` anchors at the LOWEST joints instead. Together these make drags HEAL a floating figure rather than preserve it — pins that anchored "wherever the foot currently is" let per-drag residuals compound until the figure floated (once past the contact threshold nothing anchored it at all, and each gentle pull swung the airborne body further). **Shared widgets** (`src/widgets/`): app-standard custom controls reusable across panels. `DragNumberBox` (`dragnumberbox.{h,cpp}`) is **the standard control for any bounded scalar parameter row** — use it instead of a `QSlider`/`QDoubleSpinBox` pair. It's a DCC-style scrub field: a left-to-right range fill (progress-bar style, `(value-min)/(max-min)`, in the app's muted accent `#314D7A`) behind a centered value label; press+horizontal-drag scrubs the value, and a plain click (no drag) opens inline type-in editing (Enter/focus-out commits, Esc cancels). The widget cursor is the left-right arrow (set once in the ctor) so scrubbability is visible on hover — the one deliberate exception to the app's arrow-cursor convention, since nothing else about a filled bar says "drag me"; the inline editor keeps its own I-beam. API mirrors the `QDoubleSpinBox` essentials (`setRange`/`setSingleStep`/`setDecimals`/`setValue`/`valueChanged`), so swapping one in is mechanical — see `EnvironmentPanel::addValueRow` for the row-builder pattern. It paints itself in C++ (no QSS rules needed); its colors are `Q_PROPERTY`s (the `AssetTreeView` pattern) with defaults matching the app palette, so a container can re-theme it via `qproperty-fillColor:` etc. if ever needed.

**Constants** (`src/constants.h`): shared UI dimensions, colors, and timing values live here rather than being duplicated as magic numbers across widgets/delegates — add new shared layout/color/timing constants here instead of inlining them.
